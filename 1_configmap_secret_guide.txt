===============================================================================
 PRACTICAL 7 (Part 1): Kubernetes Configuration Management
                   ConfigMaps & Secrets — Step-by-Step Guide
===============================================================================

Objective:
  Learn how to separate configuration from container images using Kubernetes
  ConfigMaps (non-sensitive data) and Secrets (sensitive data like passwords).
  Inject configuration as environment variables AND as mounted files (volumes).

  What is Configuration Management in Kubernetes?
  In Docker, configuration (environment variables, config files) is often baked
  into the image. This is bad because:
    - Changing config requires rebuilding the image
    - Same image cannot be used in dev, staging, and production
    - Sensitive data (passwords) should NOT be in images

  Kubernetes solves this with:
    ConfigMap  → stores non-sensitive config (app mode, welcome message, URLs)
    Secret     → stores sensitive data (passwords, API keys, certificates)

  Both can be injected into pods as:
    1. Environment variables  (env / envFrom)
    2. Mounted files          (volumes)


===============================================================================
 CONFIGMAP vs SECRET — KEY DIFFERENCES
===============================================================================

  Property          ConfigMap                     Secret
  --------------    ----------------------------  ------------------------------
  Purpose           Non-sensitive configuration   Sensitive data (passwords, keys)
  Data encoding     Plain text                    Base64 encoded
  Access            Same as any K8s resource      More restricted (RBAC recommended)
  Example values    APP_MODE=development          DB_PASSWORD=LabPass@123
                    WELCOME_MESSAGE=Hello        API_KEY=sk-abc123xyz
  Injection         env vars, volume mount         env vars, volume mount
  File on disk      Readable text                  Base64 encoded (decoded when mounted)

  RULE OF THUMB:
    If it is NOT sensitive → ConfigMap
    If it IS sensitive     → Secret

 STEP 1: Create the ConfigMap
===============================================================================

A ConfigMap stores non-sensitive configuration as key-value pairs.

File: app-config.yaml
-------------------------------------------------------------------------------
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  APP_MODE: "development"
  WELCOME_MESSAGE: "Hello from Kubernetes ConfigMap"
-------------------------------------------------------------------------------

Explanation:
  - kind: ConfigMap     : This is a ConfigMap resource.
  - name: app-config   : The name we will reference in the deployment.
  - data:               : Key-value pairs of configuration.
  - APP_MODE            : Application mode (development/production).
  - WELCOME_MESSAGE     : A message displayed on the web page.

Apply the ConfigMap:

Command:
  kubectl apply -f app-config.yaml

Verify:

Command:
  kubectl get configmap

Expected output:
  NAME         DATA   AGE
  app-config   2      5s

View the details:

Command:
  kubectl describe configmap app-config

Expected output:
  Name:         app-config
  Data:
  APP_MODE:        development
  WELCOME_MESSAGE: Hello from Kubernetes ConfigMap


===============================================================================
 STEP 2: Create the Secret
===============================================================================

A Secret stores sensitive data. In this example, database credentials.

File: app-secret.yaml
-------------------------------------------------------------------------------
apiVersion: v1
kind: Secret
metadata:
  name: app-secret
type: Opaque
stringData:
  DB_USERNAME: "labuser"
  DB_PASSWORD: "LabPass@123"
-------------------------------------------------------------------------------

Explanation:
  - kind: Secret        : This is a Secret resource.
  - name: app-secret   : The name we will reference in the deployment.
  - type: Opaque       : Generic secret type (for key-value pairs).
  - stringData:         : Plain text values. Kubernetes automatically encodes
                          them to Base64 internally. You do NOT need to
                          base64-encode them yourself when using stringData.
  - DB_USERNAME        : Database username.
  - DB_PASSWORD        : Database password (sensitive — stored as Secret).

Apply the Secret:

Command:
  kubectl apply -f app-secret.yaml

Verify:

Command:
  kubectl get secrets

Expected output:
  NAME        TYPE     DATA   AGE
  app-secret  Opaque   2      5s

View the details:

Command:
  kubectl describe secret app-secret

Expected output:
  Name:       app-secret
  Type:       Opaque
  Data:
  DB_PASSWORD:  11 bytes      <-- shows length, NOT the actual value
  DB_USERNAME:  7 bytes       <-- shows length, NOT the actual value

KEY OBSERVATION:
  kubectl describe does NOT show the actual secret values (for security).
  It only shows the byte length. This is a security feature.

If you want to see the actual values (for debugging):

Command:
  kubectl get secret app-secret -o jsonpath="{.data.DB_PASSWORD}" | base64 --decode

Expected output:
  LabPass@123


===============================================================================
 STEP 3: Create the Deployment (Uses ConfigMap + Secret)
===============================================================================

This deployment creates Nginx pods that:
  1. Read config values from ConfigMap as ENVIRONMENT VARIABLES
  2. Read secret values from Secret as ENVIRONMENT VARIABLES
  3. ALSO mount the ConfigMap and Secret as FILES (volumes)
  4. Write an HTML page that displays the config values

File: config-app-deployment.yaml
-------------------------------------------------------------------------------
apiVersion: apps/v1
kind: Deployment
metadata:
  name: config-app
spec:
  replicas: 2
  selector:
    matchLabels:
      app: config-app
  template:
    metadata:
      labels:
        app: config-app
    spec:
      containers:
      - name: web
        image: nginx:alpine
        command: ["/bin/sh", "-c"]
        args:
        - |
          cat > /usr/share/nginx/html/index.html <<EOF
          <html>
          <body>
            <h1>Configuration Management Demo</h1>
            <p>Mode: ${APP_MODE}</p>
            <p>${WELCOME_MESSAGE}</p>
            <p>DB User configured: ${DB_USERNAME}</p>
            <p>DB Password: [MASKED]</p>
          </body>
          </html>
          EOF
          nginx -g 'daemon off;'
        env:
        - name: APP_MODE
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: APP_MODE
        - name: WELCOME_MESSAGE
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: WELCOME_MESSAGE
        - name: DB_USERNAME
          valueFrom:
            secretKeyRef:
              name: app-secret
              key: DB_USERNAME
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: app-secret
              key: DB_PASSWORD
        ports:
        - containerPort: 80
        volumeMounts:
        - name: secret-volume
          mountPath: /etc/app-secret
          readOnly: true
        - name: config-volume
          mountPath: /etc/app-config
          readOnly: true
      volumes:
      - name: secret-volume
        secret:
          secretName: app-secret
      - name: config-volume
        configMap:
          name: app-config
-------------------------------------------------------------------------------

DETAILED EXPLANATION:

  ENVIRONMENT VARIABLE INJECTION (env + valueFrom):

    - name: APP_MODE
      valueFrom:
        configMapKeyRef:        ← Reads from ConfigMap
          name: app-config      ← ConfigMap name
          key: APP_MODE         ← Key inside the ConfigMap

    - name: DB_USERNAME
      valueFrom:
        secretKeyRef:           ← Reads from Secret
          name: app-secret      ← Secret name
          key: DB_USERNAME       ← Key inside the Secret

    So inside the container, these env vars are available:
      APP_MODE=development
      WELCOME_MESSAGE=Hello from Kubernetes ConfigMap
      DB_USERNAME=labuser
      DB_PASSWORD=LabPass@123

  HTML GENERATION:
    The args section writes an HTML page using ${APP_MODE}, ${WELCOME_MESSAGE},
    and ${DB_USERNAME} from the environment variables. The DB password is
    shown as [MASKED] — it is injected as an env var but NOT displayed on the
    page. This demonstrates that secrets are available to the app but should
    not be exposed to users.

  VOLUME MOUNT INJECTION (volumeMounts + volumes):

    - name: config-volume
      mountPath: /etc/app-config   ← ConfigMap mounted as files here
      readOnly: true

    - name: secret-volume
      mountPath: /etc/app-secret   ← Secret mounted as files here
      readOnly: true

    volumes:
    - name: config-volume
      configMap:
        name: app-config           ← Mounts the ConfigMap as files

    - name: secret-volume
      secret:
        secretName: app-secret     ← Mounts the Secret as files

    This means:
      /etc/app-config/APP_MODE         → contains "development"
      /etc/app-config/WELCOME_MESSAGE  → contains "Hello from Kubernetes ConfigMap"
      /etc/app-secret/DB_USERNAME      → contains "labuser"
      /etc/app-secret/DB_PASSWORD      → contains "LabPass@123"

    TWO WAYS TO INJECT CONFIG:
      1. Environment variables (env + valueFrom) — good for app code that
         reads env vars
      2. Volume mounts (volumeMounts + volumes) — good for config files that
         the app reads from disk

Apply the deployment:

Command:
  kubectl apply -f config-app-deployment.yaml

Verify pods:

Command:
  kubectl get pods -l app=config-app

Expected output:
  NAME                          READY   STATUS    RESTARTS   AGE
  config-app-xxxxxxxx-aaaaaa    1/1     Running   0          10s
  config-app-xxxxxxxx-bbbbbb    1/1     Running   0          10s

 STEP 6: Verify ConfigMap and Secret Files Inside the Pod
===============================================================================

The ConfigMap and Secret were also mounted as files. Let us verify.

STEP 6a: Get a pod name:

Command:
  kubectl get pods -l app=config-app

STEP 6b: List the mounted ConfigMap files:

Command:
  kubectl exec <pod-name> -- ls /etc/app-config/

Expected output:
  APP_MODE
  WELCOME_MESSAGE

STEP 6c: Read the ConfigMap files:

Command:
  kubectl exec <pod-name> -- cat /etc/app-config/APP_MODE

Expected output:
  development

Command:
  kubectl exec <pod-name> -- cat /etc/app-config/WELCOME_MESSAGE

Expected output:
  Hello from Kubernetes ConfigMap

STEP 6d: List the mounted Secret files:

Command:
  kubectl exec <pod-name> -- ls /etc/app-secret/

Expected output:
  DB_PASSWORD
  DB_USERNAME

STEP 6e: Read the Secret files:

Command:
  kubectl exec <pod-name> -- cat /etc/app-secret/DB_USERNAME

Expected output:
  labuser

Command:
  kubectl exec <pod-name> -- cat /etc/app-secret/DB_PASSWORD

Expected output:
  LabPass@123

KEY CONCEPT:
  When a Secret is mounted as a volume, the values are automatically decoded
  from Base64 back to plain text. The files contain the actual values, not
  Base64-encoded strings.


===============================================================================
 STEP 7: Update the ConfigMap and See Changes
===============================================================================

One of the main benefits of ConfigMaps is that you can update configuration
WITHOUT rebuilding the Docker image.

STEP 7a: Edit the ConfigMap:

Command:
  kubectl edit configmap app-config

This opens the ConfigMap in your default editor. Change the values:

Change:
  APP_MODE: "development"        →  APP_MODE: "production"
  WELCOME_MESSAGE: "Hello from Kubernetes ConfigMap"
    → WELCOME_MESSAGE: "Welcome to Production Environment"

Save and close the editor.

STEP 7b: Verify the change:

Command:
  kubectl get configmap app-config -o yaml

Expected output (key part):
  data:
    APP_MODE: production
    WELCOME_MESSAGE: Welcome to Production Environment

STEP 7c: Restart pods to pick up new config:

Environment variables are set at pod STARTUP. To pick up the new ConfigMap
values, we need to restart the pods:

Command:
  kubectl rollout restart deployment config-app

Check rollout status:

Command:
  kubectl rollout status deployment config-app

Expected output:
  deployment "config-app" successfully rolled out

STEP 7d: Verify the change in the browser:

  http://localhost:30080

Expected output (web page):
  Configuration Management Demo
  Mode: production
  Welcome to Production Environment
  DB User configured: labuser
  DB Password: [MASKED]

KEY CONCEPT:
  We changed the application's configuration by editing the ConfigMap — NO
  Docker image rebuild needed. This is the power of separating config from
  images. The same Docker image works in development and production — only
  the ConfigMap changes.

NOTE ON VOLUME-MOUNTED CONFIGMAPS:
  When a ConfigMap is mounted as a volume, Kubernetes automatically updates
  the files when the ConfigMap changes (after a short delay, ~1 minute).
  However, environment variables are only read at pod startup, so you need
  to restart pods for env var changes to take effect.

  DB User configured: admin        <-- changed from labuser to admin
  DB Password: [MASKED]


===============================================================================
 STEP 9: Create ConfigMap from a File (Alternative Method)
===============================================================================

Besides defining ConfigMaps in YAML, you can create them from files.

STEP 9a: Create a properties file:

File: app.properties
-------------------------------------------------------------------------------
APP_NAME=MyK8sApp
APP_VERSION=2.0
LOG_LEVEL=info
MAX_CONNECTIONS=100
-------------------------------------------------------------------------------

STEP 9b: Create ConfigMap from the file:

Command:
  kubectl create configmap app-file-config --from-file=app.properties

STEP 9c: Verify:

Command:
  kubectl get configmap app-file-config -o yaml

Expected output:
  apiVersion: v1
  kind: ConfigMap
  metadata:
    name: app-file-config
  data:
    app.properties: |
      APP_NAME=MyK8sApp
      APP_VERSION=2.0
      LOG_LEVEL=info
      MAX_CONNECTIONS=100

STEP 9d: Create ConfigMap from individual key-value pairs (command line):

Command:
  kubectl create configmap app-cli-config ^
    --from-literal=APP_NAME=MyK8sApp ^
    --from-literal=APP_VERSION=2.0

(PowerShell: use backtick ` for line continuation)

Verify:

Command:
  kubectl get configmap app-cli-config -o yaml

===============================================================================
 SUMMARY: Two Ways to Inject ConfigMap/Secret into Pods
===============================================================================

  Method 1: ENVIRONMENT VARIABLES
  -----------------------------------------------------------
  How:  env + valueFrom + configMapKeyRef / secretKeyRef
  Pros: Simple, app reads via getenv()
  Cons: Requires pod restart to pick up changes

  YAML:
    env:
    - name: APP_MODE
      valueFrom:
        configMapKeyRef:
          name: app-config
          key: APP_MODE

  Inside container: echo $APP_MODE → development

  Method 2: VOLUME MOUNT
  -----------------------------------------------------------
  How:  volumeMounts + volumes + configMap / secret
  Pros: Auto-updates when ConfigMap changes (no restart needed for volume)
        Good for config files (JSON, YAML, properties)
  Cons: Slightly more setup

  YAML:
    volumeMounts:
    - name: config-volume
      mountPath: /etc/app-config
      readOnly: true
    volumes:
    - name: config-volume
      configMap:
        name: app-config

  Inside container: cat /etc/app-config/APP_MODE → development

  Method 3: envFrom (Inject ALL keys at once)
  -----------------------------------------------------------
  How:  envFrom + configMapRef / secretRef
  Pros: Injects ALL keys from a ConfigMap/Secret as env vars at once
  Cons: All keys become env vars (no control over individual names)

  YAML:
    envFrom:
    - configMapRef:
        name: app-config
    - secretRef:
        name: app-secret


===============================================================================
 QUICK REFERENCE: ConfigMap & Secret Commands
===============================================================================

  kubectl get configmap                       List all ConfigMaps
  kubectl get cm                              Short form
  kubectl describe configmap <name>           Show ConfigMap details
  kubectl get configmap <name> -o yaml        Show full ConfigMap YAML
  kubectl edit configmap <name>               Edit a ConfigMap
  kubectl create configmap <name> --from-literal=KEY=VALUE   Create from CLI
  kubectl create configmap <name> --from-file=<path>         Create from file
  kubectl delete configmap <name>              Delete a ConfigMap

  kubectl get secret                          List all Secrets
  kubectl describe secret <name>              Show Secret (masks values)
  kubectl get secret <name> -o jsonpath="{.data.KEY}" | base64 --decode
                                               Decode a secret value
  kubectl create secret generic <name> --from-literal=KEY=VALUE
                                               Create Secret from CLI
  kubectl delete secret <name>                Delete a Secret

  kubectl rollout restart deployment <name>    Restart pods for new config
  kubectl exec <pod> -- cat /etc/app-config/KEY   Read mounted ConfigMap file
  kubectl exec <pod> -- cat /etc/app-secret/KEY   Read mounted Secret file
