===============================================================================
 PRACTICAL 7 (Part 2): Building a Custom Frontend + Backend App
                   with ConfigMaps & Secrets on Kubernetes
===============================================================================

Objective:
  If you are asked to create your OWN HTML frontend and backend application
  and manage its configuration using Kubernetes ConfigMaps and Secrets,
  this guide shows you exactly how to do it — step by step with all code.

  You will build:
    - A Frontend  (HTML page served by Nginx)
    - A Backend   (Node.js Express API that reads config from env vars)
    - A ConfigMap (stores app name, environment, theme color, log level)
    - A Secret    (stores database host, username, password)

  The backend reads configuration from environment variables that Kubernetes
  injects from the ConfigMap and Secret. The frontend calls the backend API
  and displays the config values on the page.

  When you change the ConfigMap, the app configuration changes WITHOUT
  rebuilding any Docker image.

  Architecture:

    Browser (http://localhost:30110)
      |
      v
    FRONTEND SERVICE (NodePort 30110)
      |
      v
    FRONTEND PODS (Nginx, 2 replicas)
      |  Proxies /api/ to "config-backend-svc" (service discovery)
      v
    BACKEND SERVICE (ClusterIP)
      |
      v
    BACKEND PODS (Node.js, 2 replicas)
      |  Reads config from ENV VARS injected by Kubernetes
      |
      +-- APP_NAME, APP_ENV, THEME_COLOR, LOG_LEVEL  ← from ConfigMap
      +-- DB_HOST, DB_USER, DB_PASSWORD              ← from Secret
      |
      +-- ConfigMap also mounted as FILES at /etc/app-config/
      +-- Secret also mounted as FILES at /etc/app-secret/

===============================================================================
 STEP 2: BACKEND — Create server.js
===============================================================================

This is the core of the demo. The backend reads configuration from
environment variables that Kubernetes injects from ConfigMap and Secret.

File: config-demo/backend/server.js
-------------------------------------------------------------------------------
const express = require("express");
const cors = require("cors");

const app = express();
const PORT = 5000;

// Middleware
app.use(cors());
app.options("*", cors());

// ============================================================
// READ CONFIGURATION FROM ENVIRONMENT VARIABLES
// These are injected by Kubernetes from ConfigMap and Secret
// ============================================================

// ConfigMap values (non-sensitive)
const APP_NAME    = process.env.APP_NAME    || "NOT SET";
const APP_ENV     = process.env.APP_ENV     || "NOT SET";
const THEME_COLOR = process.env.THEME_COLOR || "#000000";
const LOG_LEVEL   = process.env.LOG_LEVEL   || "info";

// Secret values (sensitive)
const DB_HOST     = process.env.DB_HOST     || "NOT SET";
const DB_USER     = process.env.DB_USER     || "NOT SET";
const DB_PASSWORD = process.env.DB_PASSWORD || "NOT SET";

console.log(`[${LOG_LEVEL}] Starting ${APP_NAME} in ${APP_ENV} mode`);
console.log(`[${LOG_LEVEL}] DB Host: ${DB_HOST}, DB User: ${DB_USER}`);

// ============================================================
// API ENDPOINTS
// ============================================================

// Health check
app.get("/api/health", (req, res) => {
    res.json({ status: "Backend is running!" });
});

// Return config values (password is MASKED for security)
app.get("/api/config", (req, res) => {
    res.json({
        // From ConfigMap (safe to show)
        appName:    APP_NAME,
        appEnv:     APP_ENV,
        themeColor: THEME_COLOR,
        logLevel:   LOG_LEVEL,

        // From Secret (host and user OK, password MASKED)
        dbHost:     DB_HOST,
        dbUser:     DB_USER,
        dbPassword: "******** (masked — injected via Secret)",

        // Proof that env vars came from K8s
        source: {
            appName:    "ConfigMap: app-config",
            appEnv:     "ConfigMap: app-config",
            themeColor: "ConfigMap: app-config",
            logLevel:   "ConfigMap: app-config",
            dbHost:     "Secret: db-secret",
            dbUser:     "Secret: db-secret",
            dbPassword: "Secret: db-secret"
        }
    });
});

app.listen(PORT, () => {
    console.log(`Backend running on port ${PORT}`);
});
-------------------------------------------------------------------------------

DETAILED EXPLANATION:

  READING ENV VARS:
    - process.env.APP_NAME  : Reads the APP_NAME environment variable.
      If Kubernetes injects it (from ConfigMap), the value appears.
      If NOT injected, it falls back to "NOT SET" (the || "NOT SET" part).
    - Same pattern for all other variables.

  WHY ENV VARS?
    Kubernetes injects ConfigMap and Secret values as environment variables
    in the pod spec. The app reads them with process.env. This is the
    standard way applications consume configuration in containers.

  THE /api/config ENDPOINT:
    Returns all config values as JSON. The frontend fetches this and
    displays it. The DB password is MASKED — even though the app has it
    (in DB_PASSWORD env var), it does NOT send it to the frontend.
    This demonstrates that secrets are available to the app but should
    not be exposed to users.

  THE /api/health ENDPOINT:
    Simple health check — returns {"status": "Backend is running!"}.
    Used to verify the backend is alive.

 STEP 3: BACKEND — Create Dockerfile
===============================================================================

File: config-demo/backend/Dockerfile
-------------------------------------------------------------------------------
FROM node:20-alpine

WORKDIR /app

COPY package.json ./

RUN npm install

COPY server.js .

EXPOSE 5000

CMD ["node", "server.js"]
-------------------------------------------------------------------------------

Explanation:
  - node:20-alpine  : Lightweight Node.js image.
  - COPY package.json first, then npm install : Layer caching — if
    server.js changes but package.json doesn't, npm install is cached.
  - EXPOSE 5000     : The Express server listens on port 5000.
  - CMD node server.js : Start the server.

NOTE: No config values in the Dockerfile. Config is injected at RUNTIME
      by Kubernetes, not at BUILD time. This is the key principle.

 STEP 5: FRONTEND — Create nginx.conf
===============================================================================

File: config-demo/frontend/nginx.conf
-------------------------------------------------------------------------------
server {
    listen 80;

    location / {
        root /usr/share/nginx/html;
        index index.html;
    }

    # Proxy /api/ requests to the backend Service
    # "config-backend-svc" is the Kubernetes Service name
    # Kubernetes DNS resolves it (service discovery)
    location /api/ {
        proxy_pass http://config-backend-svc:5000/api/;
        proxy_set_header Host $host;
    }
}
-------------------------------------------------------------------------------

Explanation:
  - location /       → serve index.html
  - location /api/   → proxy to "config-backend-svc:5000"
    "config-backend-svc" is the Kubernetes Service name (service discovery).
    The frontend does NOT know the backend pod IP — just the service name.

===============================================================================
 STEP 10: KUBERNETES — Backend Deployment (Injects ConfigMap + Secret)
===============================================================================

This is the most important file. It shows how to inject ConfigMap and Secret
values as environment variables AND as volume mounts.

File: config-demo/k8s/backend-deployment.yaml
-------------------------------------------------------------------------------
apiVersion: apps/v1
kind: Deployment
metadata:
  name: config-backend
spec:
  replicas: 2
  selector:
    matchLabels:
      app: config-backend
  template:
    metadata:
      labels:
        app: config-backend
    spec:
      containers:
      - name: backend
        image: config-demo-backend:1.0
        imagePullPolicy: IfNotPresent
        ports:
        - containerPort: 5000
        env:
        # --- ConfigMap values (non-sensitive) ---
        - name: APP_NAME
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: APP_NAME
        - name: APP_ENV
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: APP_ENV
        - name: THEME_COLOR
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: THEME_COLOR
        - name: LOG_LEVEL
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: LOG_LEVEL
        # --- Secret values (sensitive) ---
        - name: DB_HOST
          valueFrom:
            secretKeyRef:
              name: db-secret
              key: DB_HOST
        - name: DB_USER
          valueFrom:
            secretKeyRef:
              name: db-secret
              key: DB_USER
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: db-secret
              key: DB_PASSWORD
        # --- Also mount as files (volume) ---
        volumeMounts:
        - name: config-volume
          mountPath: /etc/app-config
          readOnly: true
        - name: secret-volume
          mountPath: /etc/app-secret
          readOnly: true
      volumes:
      - name: config-volume
        configMap:
          name: app-config
      - name: secret-volume
        secret:
          secretName: db-secret
-------------------------------------------------------------------------------

DETAILED EXPLANATION:

  INJECTING AS ENVIRONMENT VARIABLES (env + valueFrom):

    - name: APP_NAME
      valueFrom:
        configMapKeyRef:        ← Reads from ConfigMap
          name: app-config      ← ConfigMap name (must match Step 8)
          key: APP_NAME         ← Key inside the ConfigMap

    - name: DB_HOST
      valueFrom:
        secretKeyRef:           ← Reads from Secret
          name: db-secret       ← Secret name (must match Step 9)
          key: DB_HOST          ← Key inside the Secret

    Inside the container, these become env vars:
      APP_NAME=Config Demo App
      APP_ENV=development
      THEME_COLOR=#e94560
      LOG_LEVEL=info
      DB_HOST=postgres.database.svc.cluster.local
      DB_USER=appuser
      DB_PASSWORD=SuperSecret@789

    The Node.js code reads them with process.env.APP_NAME, etc.

  INJECTING AS FILES (volumeMounts + volumes):

    - name: config-volume
      mountPath: /etc/app-config    ← ConfigMap mounted here as files
      readOnly: true

    - name: secret-volume
      mountPath: /etc/app-secret    ← Secret mounted here as files
      readOnly: true

    volumes:
    - name: config-volume
      configMap:
        name: app-config            ← Mounts ConfigMap as files
    - name: secret-volume
      secret:
        secretName: db-secret       ← Mounts Secret as files

    Inside the container, files appear:
      /etc/app-config/APP_NAME       → contains "Config Demo App"
      /etc/app-config/APP_ENV        → contains "development"
      /etc/app-config/THEME_COLOR    → contains "#e94560"
      /etc/app-config/LOG_LEVEL      → contains "info"
      /etc/app-secret/DB_HOST        → contains "postgres.database..."
      /etc/app-secret/DB_USER        → contains "appuser"
      /etc/app-secret/DB_PASSWORD    → contains "SuperSecret@789"

  WHY BOTH METHODS?
    This demo shows BOTH injection methods so you can explain both to faculty.
    In practice, you would use whichever method your app supports:
      - Env vars: good for apps that read config from env (like our Node.js app)
      - Files: good for apps that read config files (JSON, YAML, .properties)

===============================================================================
 STEP 19: Alternative — envFrom (Inject ALL Keys at Once)
===============================================================================

Instead of listing each key individually, you can inject ALL keys from a
ConfigMap or Secret at once using envFrom.

Alternative backend deployment (envFrom approach):
-------------------------------------------------------------------------------
apiVersion: apps/v1
kind: Deployment
metadata:
  name: config-backend
spec:
  replicas: 2
  selector:
    matchLabels:
      app: config-backend
  template:
    metadata:
      labels:
        app: config-backend
    spec:
      containers:
      - name: backend
        image: config-demo-backend:1.0
        imagePullPolicy: IfNotPresent
        ports:
        - containerPort: 5000
        envFrom:
        - configMapRef:
            name: app-config
        - secretRef:
            name: db-secret
-------------------------------------------------------------------------------

Explanation:
  - envFrom + configMapRef : Injects ALL keys from the ConfigMap as env vars.
    So APP_NAME, APP_ENV, THEME_COLOR, LOG_LEVEL all become env vars.
  - envFrom + secretRef    : Injects ALL keys from the Secret as env vars.
    So DB_HOST, DB_USER, DB_PASSWORD all become env vars.

  This is shorter but less control — you can't rename keys or pick subsets.

  The individual env + valueFrom approach (used in Step 10) gives you
  more control: you can rename keys, pick specific keys, and add defaults.

===============================================================================
 HOW TO ADAPT THIS FOR YOUR OWN APP
===============================================================================

If you need to create your OWN frontend and backend with ConfigMaps and
Secrets, follow this checklist:

1. CREATE YOUR HTML FRONTEND:
   - Write your index.html (any design you want)
   - Write nginx.conf (proxy /api/ to your backend service name)
   - Write Dockerfile (FROM nginx:alpine, COPY files)

2. CREATE YOUR BACKEND:
   - Write your server code (Node.js, Python, Java, etc.)
   - Read config from environment variables:
       Node.js:  process.env.MY_CONFIG
       Python:   os.environ.get("MY_CONFIG")
       Java:     System.getenv("MY_CONFIG")
   - Do NOT hardcode config values in code
   - Write Dockerfile

3. CREATE CONFIGMAP (non-sensitive config):
   - List all non-sensitive config as key-value pairs
   - Example: APP_NAME, APP_VERSION, API_TIMEOUT, LOG_LEVEL

4. CREATE SECRET (sensitive config):
   - List all sensitive data as key-value pairs
   - Example: DB_PASSWORD, API_KEY, JWT_SECRET

5. CREATE DEPLOYMENT YAML:
   - Reference your Docker image
   - Add env: section with configMapKeyRef and secretKeyRef
   - (Optional) Add volumeMounts for file-based config

6. CREATE SERVICE YAML:
   - ClusterIP for backend (internal)
   - NodePort for frontend (browser access)

7. BUILD IMAGES:
   - docker build -t your-backend:1.0 ./backend
   - docker build -t your-frontend:1.0 ./frontend

8. DEPLOY:
   - kubectl apply -f k8s/

9. TEST:
   - Open browser at http://localhost:<nodePort>
   - Verify config values appear on the page

10. UPDATE CONFIG (without rebuilding images):
    - kubectl edit configmap <name>
    - kubectl rollout restart deployment <name>
    - Refresh browser — new config appears


===============================================================================
 CONFIGMAP vs SECRET — DECISION GUIDE
===============================================================================

  Put it in a ConfigMap if...            Put it in a Secret if...
  -----------------------------------    -----------------------------------
  It is not a password                   It is a password
  It is not an API key                   It is an API key
  It is not a private key                It is a private key / certificate
  It is not a token                      It is an auth token
  It is OK for anyone to see it          It must be kept hidden
  Example: APP_NAME=MyApp               Example: DB_PASSWORD=secret123
  Example: LOG_LEVEL=info                Example: API_KEY=sk-abc123
  Example: MAX_RETRIES=3                Example: JWT_SECRET=xyz789


===============================================================================
 FACULTY VIVA Q&A
===============================================================================

Q1: What is a ConfigMap and why do we use it?
A:  A ConfigMap stores non-sensitive configuration as key-value pairs.
    We use it to separate configuration from the container image. The same
    Docker image can run in different environments (dev, staging, prod) with
    different ConfigMaps — no rebuild needed.

Q2: What is a Secret and how is it different from a ConfigMap?
A:  A Secret stores sensitive data (passwords, keys, tokens). It is similar
    to a ConfigMap but values are Base64-encoded, access can be restricted
    with RBAC, and you should never commit Secret YAML files with real
    values to version control.

Q3: How does the backend read ConfigMap/Secret values?
A:  Kubernetes injects the values as environment variables in the pod spec.
    The backend code reads them with process.env.KEY (Node.js),
    os.environ.get("KEY") (Python), or System.getenv("KEY") (Java).
    The code has no idea whether the value came from a ConfigMap or Secret.

Q4: What are the two ways to inject ConfigMap/Secret into pods?
A:  1. Environment variables (env + valueFrom) — read by app code as env vars.
    2. Volume mounts (volumeMounts + volumes) — appear as files on disk.
    Both methods are demonstrated in this practical.

Q5: What happens when you update a ConfigMap?
A:  If injected as env vars: you need to restart pods (kubectl rollout restart)
    because env vars are read at startup. If mounted as a volume: Kubernetes
    auto-updates the files after a short delay (~1 min), but the app needs to
    re-read the file to pick up changes.

Q6: How did we prove the config injection worked?
A:  The frontend page shows the config values (App Name, Environment, etc.)
    fetched from the backend API. The backend read them from env vars that
    Kubernetes injected from the ConfigMap. When we changed the ConfigMap
    and restarted, the page showed the new values — without rebuilding images.

Q7: Why is the DB password masked on the page?
A:  The backend has the password (in the DB_PASSWORD env var) but does NOT
    send it to the frontend. It returns "******** (masked)" instead. This
    shows that secrets are available to the application code but should not
    be exposed to end users.

Q8: What is envFrom and how is it different from env + valueFrom?
A:  envFrom injects ALL keys from a ConfigMap or Secret as env vars at once.
    env + valueFrom lets you inject individual keys with full control (rename,
    select specific keys, add defaults). envFrom is shorter but less flexible.

Q9: How would you use this in production?
A:  Use ConfigMaps for app settings (timeouts, feature flags, log levels).
    Use Secrets for credentials (DB passwords, API keys, TLS certs). Use
    envFrom for bulk injection or env for selective injection. Never store
    secrets in ConfigMaps or in container images. Use external secret
    managers (Vault, AWS Secrets Manager) for production-grade secret management.
